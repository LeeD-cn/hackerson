# 项目启动说明：多人 AI Coding 协作框架

你现在接手一个正在参加 AI Coding 黑客松的项目。请先理解以下产品设计与约束，再检查当前代码仓库，并在此基础上推进实现。

**重要约束：开发时间非常有限，必须优先复用 Git、现有开发工具和成熟技术，不要过度设计。我们的目标是完成一个真实可运行的 MVP，而不是只做静态原型。**

## 一、项目目标

我们要开发一个面向多人 AI Coding 的项目协作框架。

实际开发中，团队成员各自使用 Codex 等 AI Coding 工具负责不同的开发任务，但不同智能体之间存在以下问题：

1. 各自的实现方式、代码规范和接口设计容易不一致，难以整合。
2. 成员无法直接了解其他智能体的工作进度和实现细节，依赖人工转述。
3. 更换模型或开启新对话后，原有工作上下文容易丢失。
4. 全局架构调整难以及时通知所有受影响的任务，容易出现接口不一致。
5. 不同 AI Coding 工具之间缺乏统一的项目协作接口。

我们的核心思想是：

**项目任务模块拥有稳定的身份、职责、上下文和权限；Codex 等智能体只是可随时替换的执行者。**

即使一个任务的执行者更换了，新的智能体也应该能够通过 MCP 获取该任务的必要上下文、当前状态、接口契约和待办事项，继续原有工作，而不必依赖原来的聊天记录。

整个系统分为两个组成部分：

- **后台项目管理系统（Host / Control Plane）**：负责项目组织、任务管理、通信、权限、上下文管理、代码审核和集成。
- **子任务 Agent**：每个成员使用自己的 Codex，通过 MCP 访问后台，获取任务上下文，执行代码开发并提交 Git。

MCP 负责提供标准化工具接口；真正的任务状态、权限判断、消息记录、上下文存储和变更管理由我们自己的后台实现。

## 二、后台的四个功能区

### 功能区 1：任务与模块规划、分配

由后台主 Agent 1 负责。

用户可以直接与主 Agent 1 对话，描述项目目标、需求和约束，由其辅助规划任务拆分和模块关系。

同时，用户也可以通过图形化界面直接创建、修改、删除任务模块，调整任务分配与依赖关系。

任务模块必须自由可定义，不预设固定的 frontend、backend、test 等模块。可以按照功能、技术组件或具体开发任务进行拆分，也可以继续拆分子任务。

每个任务模块至少包含：

- 唯一 `task_id`
- 任务名称与目标
- 任务详细描述及验收标准
- 任务依赖关系
- 当前进度与状态
- 相关接口契约和技术约束
- 关键决策与待办事项
- 当前执行者信息（可选）
- 关联 Git 分支、提交或变更请求（可选）

任务可以处于待开始、进行中、待审核、已完成、阻塞等状态。

用户手动调整任务划分后，后台应更新任务数据和依赖关系，并通过功能区 2 通知受影响的子任务 Agent。

### 功能区 2：通信与权限管理

由后台主 Agent 1 负责协调，后台服务负责实际执行。

这是整个项目的核心功能之一。

子任务 Agent 不直接访问其他任务的私有上下文，而是通过统一的 MCP 工具向后台提出请求。

通信需要支持以下场景：

**1. 子任务向主 Agent 1 提问**

主 Agent 1 根据全局上下文、项目规范和任务规划，优先直接回答问题。

**2. 跨任务查询**

如果主 Agent 1 无法回答，且问题涉及其他任务的具体实现，主 Agent 1 通过后台上下文服务读取有权限访问的目标任务信息，再将必要的信息转发给请求方。

例如，任务 A 需要了解任务 B 的 API 字段，但 A 无权直接读取 B 的完整上下文。系统可以允许 A 查询 B 的公开接口契约，并由主 Agent 1 转发必要的结果。

**3. 子任务提交建议**

子任务 Agent 可以提出接口修改、任务重新划分或架构调整建议。

建议本身不自动生效。涉及全局任务划分和架构约束的变更，必须经过用户人工审核，或者遵循用户明确授权的审批规则。

**4. 广播项目变更**

用户批准变更，或者用户直接修改任务规划后，后台应：

- 更新正式任务数据与相关决策记录。
- 识别受影响的任务模块。
- 向受影响的子任务发送变更通知。
- 记录通知、确认和执行状态。
- 在界面上显示尚未确认或尚未完成迁移的任务。

不能把消息成功发送等同于任务已经完成修改。

**5. 进度查询与状态报告**

子任务 Agent 可以报告进度、阻塞、完成情况和待解决问题。主 Agent 1 可以汇总这些信息，形成项目整体状态。

第一版不需要实现复杂的远程 Agent 唤醒机制。跨任务通信可以先采用共享后台中的消息记录、上下文查询与响应机制。

### 功能区 3：上下文记忆管理

由后台主 Agent 1 负责协调，后台服务负责存储、读取、更新和权限检查。

上下文必须与任务身份绑定，而不是绑定某次 Codex 对话。

#### 3.1 每个任务的独立上下文

每个任务模块都拥有逻辑独立的上下文，至少包括：

- 任务目标和验收标准。
- 当前进度、已完成工作和待办事项。
- 接口契约、技术约束和依赖信息。
- 关键设计决策及其来源。
- 已知问题、失败尝试和阻塞事项。
- 关联代码变更及 Git 状态。

子任务 Agent 可以通过 MCP 读取和更新自己任务的上下文与进度。

每次更新应有明确的任务归属，必要时记录版本或更新时间。

#### 3.2 全局上下文

后台还需要维护独立的全局上下文，记录：

- 项目总体目标。
- 技术栈和开发规范。
- 整体架构与任务依赖。
- 全局接口约束。
- 已批准的架构决策。
- 当前项目阶段与全局待办事项。

后台的两个主 Agent 均可访问全局上下文和所有任务上下文。

普通子任务 Agent 不得直接读取全局上下文或其他任务的私有上下文。它们只能通过 MCP 获取自己被授权的信息，以及由主 Agent 1 整理后提供的初始化指导和跨任务查询结果。

#### 3.3 新 Agent 的上下文初始化

当创建新任务或新的子任务 Agent 接手已有任务时，后台应提供上下文初始化能力。

Agent 通过 MCP 拉取对应任务的启动上下文，其中包括：

1. 项目相关的全局规范摘要。
2. 当前任务目标、职责与验收标准。
3. 当前任务的上下文和完成状态。
4. 相关依赖模块的必要接口信息。
5. 最近的正式决策和架构变更。
6. 当前待办事项、阻塞问题和下一步建议。
7. 相关 Git 分支或提交信息（如果已经存在）。

启动上下文应根据当前任务实时生成，不应仅仅复制旧 Agent 的聊天记录。

#### 3.4 存储实现原则

为了控制开发成本，优先采用 SQLite。

可以在同一数据库中建立 `tasks`、`task_contexts`、`messages`、`decisions`、`change_requests` 等表，以 `task_id` 区分任务上下文。

不需要在 MVP 阶段为每个任务物理创建独立数据库。

所有访问都必须通过后台接口完成，不能因为不同 Agent 使用同一个 MCP Server，就允许它们直接读取所有数据库记录。

### 功能区 4：代码集成与审核

由后台主 Agent 2 负责。

主 Agent 2 与主 Agent 1 拥有相同范围的项目上下文访问权限，但职责不同：

- 主 Agent 1 负责项目规划、通信协调和上下文管理。
- 主 Agent 2 负责代码审核、集成、合并和必要的重构建议。

主 Agent 2 需要处理子任务提交的代码变更，检查：

- 是否满足任务目标和验收标准。
- 是否通过相关测试。
- 是否符合公共接口契约。
- 是否违反全局编码规范或架构约束。
- 是否影响其他任务模块。

通过审核后，使用现有 Git 工作流进行集成，记录审核结果和对应的提交信息。

优先复用 Git 的分支、提交、diff 和合并能力，不要自行开发版本控制系统。

对于有风险的架构变更、破坏性接口变更或审核不通过的提交，应阻止直接合并，并给出具体反馈。

自动重构是次要能力。第一版优先保证代码变更审核和集成流程可运行，不要为了实现自主重构而拖延核心功能。

主 Agent 2 在第一版中可以作为一个职责明确的审核角色，由后台工作流调用，不要求必须拥有独立、持续运行的自主会话。

## 三、子任务 Agent 的职责与工作流程

子任务 Agent 是具体的开发执行者，不负责管理整个项目。

每个子任务 Agent 只需要：

1. 通过 MCP 获取自己任务的初始化上下文。
2. 理解任务目标、验收标准、依赖和公共规范。
3. 根据需要，通过通信接口向主 Agent 1 查询问题。
4. 按照分配的任务编写、修改和测试代码。
5. 通过 MCP 更新自己的任务进度和必要的工作记录。
6. 将代码提交到指定 Git 分支，或者提交变更请求。
7. 报告完成情况，等待审核和集成。

子任务 Agent 不得自行修改未经授权的全局任务规划，也不得直接访问其他任务的私有上下文。

更换 Codex 会话后，新的会话应当可以重新读取任务上下文并继续工作。

第一版不要求后台能够自动操纵每个成员正在运行的 Codex 会话。每个成员的 Codex 主动调用 MCP 工具即可。

## 四、MCP 接口设计

请根据上述工作流设计一组简单、明确、可执行的 MCP 工具。

优先考虑以下工具，名称可以根据实现规范调整：

### 任务管理与上下文

- `list_tasks`：列出当前项目任务及其基本状态。
- `get_my_context`：获取当前任务的启动上下文。
- `get_task_status`：查询有权限访问的任务状态。
- `update_my_context`：更新当前任务的工作记录、进度和待办事项。

### 通信与协调

- `query_module`：向后台提出跨模块查询请求。
- `send_message`：向目标模块或主 Agent 发送消息。
- `report_status`：报告当前任务的进度、完成状态或阻塞问题。
- `propose_change`：提出接口、架构或任务规划变更。

### 代码集成

- `submit_change`：提交代码变更信息或关联 Git 提交。
- `get_review_feedback`：获取代码审核反馈。

不必机械地实现所有工具。请根据 MVP 的时间约束，优先实现能够跑通完整工作流的最小集合。

MCP 工具应通过后台服务访问数据库，而不是让每个 Codex 直接操作 SQLite 文件。

所有工具必须有清晰的输入参数、输出结构和错误处理。任务权限应在服务端检查，不能只依赖提示词约束。

对于跨模块查询，应由后台根据消息类型、目标模块和权限决定可以返回什么内容。

## 五、前端与可视化要求

需要一个简单的项目控制台，让用户能够：

- 查看项目总体状态。
- 以树图、节点图或其他直观方式展示任务模块及其依赖。
- 创建、修改和删除任务模块。
- 查看任务目标、上下文摘要、进度和状态。
- 查看跨模块消息、变更建议与审批记录。
- 查看架构变更影响了哪些模块，以及哪些模块尚未确认。
- 查看代码审核与集成状态。

可以使用现有成熟的图形化组件，例如 React Flow。

界面不需要复杂，但必须与真实的后台数据连接，关键操作必须能够实际改变系统状态。

## 六、技术与实现原则

请先检查当前代码仓库，确认现有技术栈、项目结构和已经实现的功能，不要假设仓库是空的，也不要未经检查就重建项目。

优先复用现有代码、依赖和开发环境。

如果仓库没有明确的技术栈，可以考虑：

- 前端：React + TypeScript + Vite。
- 后端：FastAPI 或 Node.js，选择与当前项目最匹配的一种。
- 数据存储：SQLite。
- 智能体接入：MCP Server。
- 代码版本管理：现有 Git 仓库。

不要同时引入多个后端框架，也不要在 MVP 阶段使用复杂的分布式消息队列、独立向量数据库或大型智能体编排框架。

不同模块之间的真实状态以后台数据库为准；代码状态以 Git 为准；上下文和决策记录不能取代真实代码与测试结果。

## 七、开发优先级与验收标准

我们需要在极短时间内完成可运行的 MVP。请严格按以下优先级执行。

### P0：必须完成

1. 任务模块可以动态创建和修改。
2. 任务数据、状态与上下文能够持久化。
3. MCP Server 可以让 Codex 读取并更新对应任务的上下文。
4. 不同任务之间存在明确的上下文访问边界。
5. 子任务可以通过后台查询其他模块的必要信息。
6. 项目变更可以记录，并通知受影响的任务。
7. 前端可以查看任务组织结构和当前状态。

### P1：尽可能完成

1. 架构变更提案与人工审批。
2. 多个 Codex 通过同一个后台服务协作。
3. Git 变更审核与合并。
4. 后台主 Agent 1 辅助规划任务。
5. 后台主 Agent 2 辅助审核代码。

### P2：暂不投入主要时间

1. 自动唤醒或远程控制其他 Codex 会话。
2. 复杂的自主任务调度与动态重规划。
3. 多模型供应商和多种 IDE 的完整兼容。
4. 自主重构和复杂的自动代码修复。
5. 大型分布式架构与复杂记忆检索系统。

## 八、建议的演示场景

最终应尽可能跑通以下端到端场景：

1. 用户创建一个项目，并自由划分多个开发任务。
2. 两名成员分别使用自己的 Codex，连接同一个 MCP Server。
3. 两个 Codex 分别读取自己的任务上下文。
4. 任务 A 通过后台向任务 B 查询必要的接口信息。
5. 任务 B 提出一个接口变更建议。
6. 用户审批该建议后，后台更新正式决策并通知受影响的任务。
7. 任务 A 的 Codex 新开一个对话，通过 MCP 恢复上下文并继续开发。
8. 子任务提交 Git 变更，后台审核角色给出审核结果，并在满足条件后完成集成。

如果无法在时间内完成全部流程，优先保证任务管理、上下文恢复、跨模块通信和变更记录是真实可运行的，再补充自动化和可视化细节。

1. 当前技术栈。
2. 哪些现有功能可以直接复用。
3. 为实现 MVP，最少需要新增或修改哪些模块。
4. 推荐的数据库结构和 MCP 工具接口。
5. 按照当前剩余时间排序的实现计划。

完成这一步后，不要停留在长篇方案设计。请尽快确定最小实现方案并开始编码。

如果发现已有代码与本设计冲突，优先保留可复用的实现，并明确指出必要调整。遇到非关键选择时自行做合理决策，不要频繁等待用户确认。

最终目标是：**让多个独立的 Codex 会话通过同一个后台协作系统，围绕不同任务共享必要信息、持续保存工作上下文、协调架构变更，并使用 Git 完成代码开发与集成。**

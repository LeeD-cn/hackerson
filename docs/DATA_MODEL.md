# 数据结构 v0.1

本文件与 `contracts/schema.sql`、`contracts/requests.py`、`contracts/responses.py` 共同构成三人的起始契约。它们是待实现行为的定义，不代表服务已经具备这些能力。

## 范围与约定

- 一个后台实例管理一个项目，`project.id=1`。暂不做多项目租户；未来扩展需要统一增加 `project_id` 和权限隔离。
- 数据库只由后端打开。MCP 和前端通过 HTTP 获取授权后的数据。
- ID 由服务端生成，为不透明字符串，如 `task_...`、`chg_...`。客户端不解析 ID，也不自行指定当前身份。
- 时间使用 UTC ISO-8601 字符串；页面按本地时区显示。
- API 字段统一 `snake_case`。SQL 的 JSON 字段在 API 中返回对象，不返回 JSON 字符串。
- `parent_id` 表示子任务归属；`dependencies` 表示开发依赖，两者不等同。
- 依赖和父子关系各自必须无环。数据库只防止自引用；多节点环由 A 的服务端在事务内检查。
- 删除采用归档，保留上下文、决策与审核证据；从活跃依赖中移除，撤销任务令牌并通知受影响任务。

## 表结构

| 表 | 主键/关联 | 用途与关键字段 |
| --- | --- | --- |
| `project` | 固定 `id=1` | 项目名称、目标、私有全局上下文 `private_context`、授权摘要 `guidance`、正式规划版本 |
| `tasks` | `task_id`；可选 `parent_id` | 自由命名的任务、目标、描述、验收、发布的接口 `contract`、约束、执行者、Git 分支、状态/进度、行版本、归档标记 |
| `task_dependencies` | `(task_id, depends_on)` | 任务依赖关系；`task_id` 依赖 `depends_on` |
| `task_contexts` | `task_id` | 当前私有工作记录 `data`、独立上下文版本、更新时间 |
| `context_history` | `(task_id, version)` | 每次上下文更新的完整快照，便于追溯 |
| `credentials` | `token_hash` | 随机令牌的 SHA-256 摘要、角色、绑定任务、撤销状态；不存令牌原文 |
| `messages` | `id`；可选 `reply_to` | 发件身份、收件身份、类型、内容、时间；保留异步查询/回复 |
| `change_requests` | `id`；目标 `task_id` | 提案、理由、结构化 `patch`、基于的项目版本、人工审核状态与说明 |
| `decisions` | `id`；可选 `change_id` | 已生效决策、对应项目版本、受改动任务、操作身份、公开变更摘要 |
| `notifications` | `id`；`decision_id`、`task_id` | 某次决策对某任务的通知、版本、确认/完成时间和说明；每个决策/任务只一条 |
| `submissions` | `id`；`task_id` | Git 提交、分支、执行者自报测试、审核反馈、外部集成记录（P1） |

管理员凭据从后台环境或受保护的本地配置加载，不允许子任务领取。两个主角色的令牌为 `coordinator`、`reviewer`，子任务令牌为 `task`；它们可以被撤销或轮换。

## 三种版本分开

| 版本 | 何时增加 | 防止什么问题 |
| --- | --- | --- |
| `project.version` | 正式任务规划/规范/接口发生变化 | 旧提案批准后覆盖新的架构决定 |
| `tasks.version` | 任务字段、状态、进度更新 | 两个请求覆盖彼此对任务的更改 |
| `task_contexts.version` | 私有工作摘要更新 | 新旧 Codex 会话互相覆盖工作记录 |

更新必须携带读取时的 `expected_version`；提案携带 `expected_project_version`。不匹配返回 409，客户端重新读取并比较，不盲目重试。私有工作摘要或进度更新不增加正式项目规划版本。

## 私有上下文 `data`

八个字段都为字符串；MVP 不引入复杂文档分片或向量索引：

```json
{
  "summary": "当前实现摘要",
  "completed": "已完成的工作",
  "todos": "待办事项",
  "blockers": "阻塞与已知问题",
  "decisions": "任务内部决定及来源；不代表已批准的全局决定",
  "failed_attempts": "失败尝试和原因",
  "next_steps": "接手后先做什么",
  "git_notes": "分支、提交及待验证事项"
}
```

任务定义中的 `contract` 是明确授权发布的接口信息。私有工作记录不能自动拼到其他任务的查询响应里。

## 四组状态

| 对象 | 状态值 | 中文含义 |
| --- | --- | --- |
| 任务 | `todo / in_progress / in_review / done / blocked` | 待开始／进行中／待审核／完成／阻塞 |
| 提案 | `pending / approved / rejected` | 待审批／已批准／已拒绝 |
| 通知 | `pending → acknowledged → completed` | 待确认／已确认理解／已完成修改 |
| 代码提交（P1） | `pending → approved 或 changes_requested`；`approved → integrated` | 待审核／通过或需修改；通过后登记集成 |

通知确认与任务完成相互独立；确认通知不会自动更改任务状态。`completed` 需要执行者说明完成的修改或为何无需修改。仍有未完成变更的任务不能直接报告 `done` 或通过代码审核。`done` 要求 `progress=100`，100% 进度不自动意味着已完成。

## 批准变更的事务边界

一次事务内：验证管理员权限 → 验证提案仍待审批及基础版本 → 检查目标任务/依赖 → 应用正式 patch → 增加任务与项目版本 → 写决策 → 计算受影响任务 → 为每个任务插入通知 → 记录提案批准身份和时间。

影响范围至少包括被改动任务、沿反向依赖可达的任务、受影响的子任务；只通知活跃任务。修改依赖时取变更前后影响集合的并集。更新全局规范时通知所有活跃任务。

任一步失败全部回滚。重复批准返回 409；不能再次生成一批通知。提案本身只入库，不改变正式任务或 `project.version`。

正式决策和通知中的公开内容必须筛选：任务只获取与自己相关的决策摘要和必要接口，不得夹带私有全局内容、其他任务的工作记录或任意管理员内部说明。

## 权限边界

| 数据/动作 | 管理员（人） | 协调主角色 | 审核主角色 | 子任务 |
| --- | --- | --- | --- | --- |
| 全局私有信息、所有任务私有上下文 | 读 | 读 | 读 | 禁止 |
| 基本任务列表/状态 | 读 | 读 | 读 | 读，限公开字段 |
| 自己的工作上下文与进度 | 可查 | 可查 | 可查 | 读写本人绑定任务 |
| 其他任务已发布接口 | 读 | 读 | 读 | 通过后端查询 |
| 直接更改规划、签发令牌、审批提案 | 允许 | 禁止，先提建议 | 禁止 | 禁止 |
| 代码审核及集成记录 | 允许 | 禁止 | 允许 | 只提交与查看本人反馈 |
| 消息/提案/通知 | 全局查看 | 全局查看 | 全局查看 | 仅发送/接收或与本人相关的记录 |

身份来自 Bearer 令牌，不能靠请求体里的 `role` 或 `task_id` 自报。SQLite 外键与 CHECK 不能替代服务端鉴权。

## Git 的证据边界

`submissions.test_results` 是执行者的陈述，审核者必须在真实仓库核对 commit、diff 和测试。`record_integration` 仅记录外部执行的 Git 集成，不执行合并，不伪称已核验代码。自动 Git 执行后续另定范围。
